# Serendipity — Design Document

*Time + place travel companion: know what the world is doing, where you are (or where you're going), when you're there.*

## 1. Concept

Most travel tools answer "where should I go?" Serendipity answers **"what is happening at this place at this time?"** — and the inverse, **"when/where should I be to catch this?"**

Two modes, one dataset:

| Mode | Input | Output |
|------|-------|--------|
| **Plan** | destination (or region) + date range, *or* a phenomenon | ranked list + calendar of phenomena overlapping the trip; best dates/places to catch a chosen phenomenon |
| **Explore** (on the road) | current GPS + "next N days" + radius | what is peaking nearby right now / soon, with travel time and odds |

Phenomenon families (v1):

- **Wildlife** — migrations (monarchs, wildebeest, gray whales, sandhill cranes), spawning/aggregations (coral spawning, salmon runs, horseshoe crabs, sardine run), blooms (bioluminescence, firefly synchrony, superblooms).
- **Astronomy** — solar/lunar eclipses, meteor showers, aurora season, supermoons, solstices/equinoxes, planetary conjunctions, dark-sky new moons.
- **Cultural** — festivals, national celebrations, religious observances, seasonal markets, sporting traditions.
- **Seasonal nature** — cherry blossom, fall foliage, lavender/tulip fields, monsoon onset, king tides, ice roads, midnight sun / polar night.

## 2. Core Domain Model

The key insight: separate the **timeless definition** of a thing from its **concrete dated windows**.

```
Phenomenon            timeless definition ("Monarch migration through central Mexico")
  └── Rule(s)         how to compute windows: fixed date, lunar, seasonal-band, astronomical table, curated list
        └── Occurrence  materialized window for one year at one place: start / peak / end + confidence
Place                 point, polygon, or named region (country/state/park) with a geohash
Source                provenance for each phenomenon/rule (URL, license, last verified)
```

### 2.1 Phenomenon
```
Phenomenon {
  id, slug, name, summary, description (md)
  family: wildlife | astronomy | cultural | seasonal
  tags: [string]                       // "whales", "dark-sky", "free", "family-friendly"
  placeIds: [PlaceId]                  // where it happens (may be many: e.g. a meteor shower is global; foliage is regional)
  rules: [Rule]
  media: [{storagePath, credit, license}]
  practical: { bestViewingTips, accessNotes, costHint, crowdLevel }
  sources: [SourceId]
  status: draft | published | archived
  contributedBy?: uid, moderatedBy?: uid
}
```

### 2.2 Rule (how Occurrences are generated)
```
Rule = 
  | FixedAnnual     { startMonthDay, endMonthDay, peakMonthDay? }                 // Diwali-like items use LunarCalendar instead
  | SeasonalBand    { typicalStart, typicalEnd, peak, varianceDays, climateNote } // foliage, blossoms, migrations
  | Lunar           { calendar: hijri|hebrew|chinese|hindu|easter, offsetDays }   // moveable feasts
  | Astronomical    { table: eclipse|meteor|moonPhase|equinox, filter }           // pulled from curated tables
  | Explicit        { windows: [{year, start, peak?, end}] }                      // one-off / hand-curated events
  | Cadence         { everyNYears, anchorYear, ...FixedAnnual }                   // World Cup, Kumbh Mela
```
Each rule carries a `confidence: high | medium | low` used for the odds indicator. A phenomenon with a `SeasonalBand` shows a *peak window ± variance*, never a single date.

### 2.3 Occurrence (materialized, queryable)
```
Occurrence {
  id: "{phenomenonId}_{placeId}_{year}"
  phenomenonId, placeId, family, tags
  start, peakStart, peakEnd, end      // Timestamps (UTC) + place tz
  confidence
  geohash (of place centroid), lat, lng, boundsRadiusKm
  monthBuckets: [int]                 // months touched -> cheap "is anything in Oct?" filters
  searchText                          // denormalized for typeahead
}
```
Occurrences are regenerated by a scheduled Cloud Function (nightly, rolling 3 years ahead). All user-facing queries hit `occurrences`, never `rules`.

### 2.4 Place
```
Place {
  id, name, kind: point | park | city | region | country | global
  lat, lng, geohash, boundsRadiusKm, geoJson? (storage ref for polygons)
  countryCode, timezone
  parentPlaceId?                      // hierarchy for "what's in Kenya" roll-ups
}
```

### 2.5 User-side
```
User        { uid, homePlaceId?, units, interests: [family|tag], proTier, notificationPrefs }
Trip        { id, ownerUid, name, legs: [{placeId, start, end}], savedOccurrenceIds, shareToken? }
Save        { uid, phenomenonId, note?, remindDaysBefore? }
Alert       { uid, kind: nearMeNow | phenomenonUpcoming | tripOverlap, params }
Contribution{ uid, type: newPhenomenon | correction | photo | report, payload, status }
Report      { uid, occurrenceId, seenAt, rating, note, photo? }   // "was it happening?" ground truth -> tunes confidence
```

## 3. Architecture

Chosen to match the team's existing stack (Flutter + Firebase, Cubit state, clean layers) so code, tooling and habits carry over.

```
┌───────────────────────── Flutter app (iOS / Android / Web) ─────────────────────────┐
│ Presentation  screens/ widgets/ ({Feature}Screen / Container / Display)              │
│ Cubits        explore, plan, phenomenon_detail, trip, search, alerts, contribute      │
│ Domain        models (Phenomenon, Occurrence, Place, Trip…), rule evaluation (pure)   │
│ Data          repositories -> Firestore | Typesense | Functions | Storage | Prefs     │
└──────────────────────────────────────────────────────────────────────────────────────┘
                │                               │
   Firebase Auth │ Firestore (source of truth)   │ Typesense Cloud (geo + time + text search index)
   Cloud Functions:                              │
     • materializeOccurrences (nightly)          │ Cloud Storage (media, geoJson polygons)
     • syncSearchIndex (Firestore trigger)       │ FCM (alerts)
     • evaluateAlerts (hourly)                   │
     • ingest/* (astronomy tables, Wikidata festivals, eBird/GBIF phenology)
```

**Why a search index (Typesense) alongside Firestore:** the core query is *geo radius × date range × families × text*. Firestore can't combine a geohash range with a date range and array filters efficiently; geohash-prefix fan-out works for "near me now" but not for "Kenya in August with wildlife". Typesense (or Algolia) handles `geo_radius + start<=X + end>=Y + family in [...]` in one call and gives typeahead for free. Firestore remains the write model; the index is derived (Functions trigger). MVP fallback if we want zero extra vendors: geohash fan-out + `monthBuckets array-contains` + client-side date filter.

**Astronomy** is computed, not curated: eclipse/meteor/moon-phase tables are ingested once (NASA, IMO) and bundled as `Astronomical` rules; visibility per place is derived (eclipse path polygon ∩ place, aurora by geomagnetic latitude band).

**Offline:** Trips download an "occurrence bundle" (JSON + thumbnails) so Explore works without signal in parks. Firestore persistence covers saves/trips.

**Platform notes**
- Web: Flutter web with hash-free URLs; deep links `/p/{slug}`, `/place/{slug}?from=&to=`, `/trip/{token}` (shareable).
- Mobile: background location *not* required for v1 — Explore alerts run on app open + optional daily FCM digest using last-known coarse location.

## 4. Product Surface (v1)

| Screen | Purpose | Key interactions |
|--------|---------|------------------|
| **Explore (Home)** | "Near me, next 14 days" | radius + horizon sliders, family chips, cards sorted by *peak proximity × distance × confidence* |
| **Map** | spatial view of Occurrences | clustered pins, time scrubber along the bottom (drag month → pins re-filter) |
| **Plan** | destination + dates, or phenomenon-first | two entry points: *"I'm going to ___ from ___ to ___"* and *"I want to see ___"* → best places/years |
| **Phenomenon detail** | everything about one thing | peak-window band chart across the year, next 3 occurrences, places, tips, sources, save/alert, add to trip |
| **Trip** | itinerary overlay | legs on a timeline with matching occurrences per leg; "shift dates" shows what you'd gain/lose |
| **Calendar** | year at a glance | 12-month heat strip per saved/interest family |
| **Contribute** | community data | propose phenomenon, correct a window, post a field report ("it's happening now") |
| **Profile / Alerts** | interests, units, notification prefs, Pro | |

Ranking score for Explore (v1, tunable in Remote Config):
```
score = w1 * peakProximity(now, peakStart, peakEnd)   // 1.0 inside peak, decays outside
      + w2 * (1 - distanceKm / radiusKm)
      + w3 * confidenceWeight
      + w4 * interestMatch(user.interests)
```

## 5. Data Strategy (the hard part)

Quality of the phenomenon catalog *is* the product. Plan:

1. **Seed catalog (curated, ~300 items)** across all four families, hand-written rules, every item with a `Source`. Target coverage: top 50 countries by tourism + globally visible astronomy.
2. **Ingest pipelines** (Functions, idempotent):
   - Astronomy: NASA eclipse catalog, IMO meteor shower calendar, computed moon phases/equinoxes.
   - Cultural: Wikidata (`instance of` festival, with `point in time`/`start time` and coordinates), national holiday APIs for moveable feasts.
   - Wildlife/seasonal: expert-curated `SeasonalBand` rules first; later, eBird/GBIF/iNaturalist observation histograms to fit peak ± variance automatically.
3. **Ground truth loop**: user `Report`s ("seen today") feed back into `SeasonalBand` variance and the confidence indicator; a moderation queue (admin web) reviews contributions.
4. **Licensing**: store license per source; only CC-BY/CC0/own content in media; text summaries are original.

## 6. Monetization (later, keep hooks now)

- Free: Explore, Plan, 1 trip, saves.
- Pro: unlimited trips, offline bundles, alerts/digests, calendar export (ICS), family sharing.
- Affiliate/partner: lodging & tour links on phenomenon detail (clearly labeled), destination-board sponsored placements.

## 7. MVP Scope & Roadmap

| Phase | Deliverable | Effort |
|-------|-------------|--------|
| **P0 — Skeleton** | Flutter project (web+iOS+Android), Firebase project, Auth (anon + Google/Apple), domain models, Firestore rules, CI (analyze/test), `materializeOccurrences` for `FixedAnnual`/`Explicit`/`Astronomical` | 1 session |
| **P1 — Catalog + Explore** | seed ~100 phenomena, Typesense index + sync, Explore screen with ranking, Phenomenon detail, Map with time scrubber | 1–2 sessions |
| **P2 — Plan + Trips** | Plan (place+dates and phenomenon-first), Trip model, shareable trip links, Calendar view, `SeasonalBand` + `Lunar` rules | 1–2 sessions |
| **P3 — Community + Alerts** | Contribute flow + moderation admin, Reports feeding confidence, FCM alerts/digests, offline bundles | 1–2 sessions |
| **P4 — Growth** | Pro paywall (RevenueCat), ICS export, ingest pipelines (Wikidata, eBird), SEO landing pages per phenomenon (Flutter web prerender or a tiny Next/Astro shell) | 1–2 sessions |

External waits to call out separately: Apple/Google developer accounts, Typesense/Algolia account, data-source API keys.

## 8. Risks & Open Questions

- **Phenology variance**: climate shift makes "peak" fuzzy; mitigated by variance bands + report loop, and by never showing a single date for `SeasonalBand` items.
- **Catalog scale vs. quality**: start narrow and curated; automation only where sources are structured (astronomy, Wikidata).
- **Search vendor**: Typesense Cloud (cheap, open-source) vs. Algolia (mature Flutter SDK) vs. Firestore-only fan-out. Recommend Typesense; decide at P1.
- **Name**: "Serendipity" is crowded on app stores — check availability early (alternatives: *Whenabouts*, *Tidewatch*, *Peakfinder*).
- **Background location**: defer; daily digest with last-known location covers most value with none of the permission friction.
